# 11. Производительность и масштаб

## Принципы
- **Событийная активация:** агенты не «крутятся» постоянно; сцену будит триггер, а продвигает Director по
  `next_turn_at` (одна выборка активных сцен за такт).
- **Один процесс** `ai-director`; Scene Engine — шаг такта с собственным бюджетом времени.
- **Сон без живых игроков** (уже есть) — сцены в каналах без читателей не создаются и ставятся на паузу.

## Лимиты (настройки админки)
| Параметр | По умолчанию (VPS 1 vCPU) | Смысл |
|---|---|---|
| Активных сцен всего | 6 | одновременно идущих |
| Активных сцен на канал | 1 (+1 ветка) | общий чат не превращается в базар |
| Шагов сцен за такт | 4 | сколько реплик готовится за такт |
| Длина сцены | 2–20 ходов, ≤ 30 мин | неактуальные закрываются |
| LLM-запросов в час | 30 (как в «Речи») | пакетная генерация: 1 запрос → 3–6 реплик |
| Контекст в LLM | ≤ 1500 токенов | профили сжаты, последние 8 ходов |
| Хранение ходов | 7 дней | потом только итоги в памяти |

## Контроль затрат на генерацию
1. Сначала план (дёшево, локально), потом текст: модель вызывается только для «важных» сцен (с живыми читателями,
   групповые G, личные D), рутина — грамматикой.
2. Пакет: один запрос на несколько ходов; кэш тем и «зародышей».
3. Деградация: нет лимита LLM → грамматика; перегрузка хоста → меньше сцен, длиннее паузы (защитник нагрузки уже есть).

## Восстановление после перезапуска
Сцены и ходы в БД; при старте — продолжить сцены с недавним `next_turn_at`, просроченные закрыть; очередь реплик
переносится из памяти процесса (`banter._queue`) в БД (`ai_scene_turns` со статусом `queued`).

## Оценка нагрузки
Шаг сцены ≈ 5–20 мс (выборки по индексам, грамматика) + LLM (асинхронно по таймауту 4 с, вне критического пути —
см. этап 03 плана). 4 шага за такт → < 100 мс без LLM. БД: +3 таблицы, ~ 10–50 тыс. строк ходов в неделю, чистка.
