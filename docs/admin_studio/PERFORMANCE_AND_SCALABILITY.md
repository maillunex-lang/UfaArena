# Производительность и масштабирование

## 1. Исходные данные [Код][Док]

- VPS: 1 vCPU, 2 ГБ RAM, swap 677 МБ, общий с другими проектами; аудит показал 30 ИИ и ~5 реальных игроков онлайн,
  БД 17 МБ (на момент аудита VPS).
- Процессы: `api` (FastAPI, планировщик внутри), `ai-director` (200 МБ, 0.3 CPU), Postgres, Redis.
- Размер текущих конфигов: roster.json 62 КБ, social.json 34 КБ, monetization.json 38 КБ, `game_overrides` —
  десятки КБ; UI-раскладка — ~3 КБ.

## 2. Оценки [Предложение]

| Параметр | Оценка | Вывод |
|---|---|---|
| Конфигов в реестре | 100–300 документов | весь активный набор < 2 МБ — держится в памяти процесса |
| Клиентский config-пакет | 20–200 КБ (JSON) | скачивается за секунды даже на 3G |
| Ассеты | сотни МБ (GLB до 40 МБ) | только через существующие пакеты с докачкой и фоновой загрузкой [Код] |
| Частота публикаций | единицы в день | нагрузка ничтожна |
| Клиенты | сотни–тысячи | проверка манифеста раз в 15 мин [Код: `POLL_INTERVAL_S`] → < 2 запросов/с на 1000 игроков; ответ кэшируется |
| Админов одновременно | 1–5 | Studio-трафик незаметен |
| Чтение конфигов игровым кодом | на каждый запрос игрока | **только из памяти процесса**; проверка версии — Redis `GET` раз в N секунд, не на каждый запрос |

## 3. Кэширование

- Сервер: активный набор конфигов в памяти каждого процесса (`api`, `ai-director`); номер активной публикации в Redis
  (`cfg:ver:<env>`); при расхождении — перечитать только изменённые конфиги.
- Манифест канала: кэш ответа в Redis/памяти, инвалидация при активации (сейчас запрос к БД на каждый `GET /manifest`
  [Код] — на сотнях игроков нормально, на тысячах — добавить кэш).
- Studio: TanStack Query (кэш, фоновое обновление), схемы конфигов кэшируются по `schema_version`.

## 4. Фоновые задачи

Через существующий планировщик `api` + таблица `studio_jobs` (лизинг, повтор): сборка config-пакетов, миниатюры,
глубокая проверка GLB/OGG, очистка просроченных preview-токенов, архивирование старых черновиков. Тяжёлое
(перекодирование картинок) — с ограничением 1 задача одновременно, чтобы не мешать игре (как `hostload` у Director
[Код]: при высокой нагрузке хоста задачи откладываются).

## 5. Мобильный холст Studio

- Рендерить только текущий экран; дерево элементов — виртуализированный список.
- Миниатюры вместо оригиналов; GLB — только по нажатию (не в списках).
- Undo/redo — команды-патчи (JSON Patch), не снимки всего документа.
- Валидация тяжёлых правил — на сервере (debounce 1–2 с), на телефоне — только схема полей.
- Цель: открытие экрана редактора < 1,5 с на среднем Android, перетаскивание 60 к/с для экранов до ~200 узлов.

## 6. Мониторинг: реальные данные отдельно от демо

Раздел мониторинга показывает только реальные источники (`job_runs`, `content_installations`, `ai_director_status`,
`/health/ready`, счётчики ошибок применения). Демонстрационные/сгенерированные показатели в Studio **запрещены**;
если источника нет — пустое состояние «нет данных», а не выдуманное число.

## 7. Хранение истории

Версии конфигов и аудит — бессрочно (объёмы малы, DATABASE §5); `content_installations` — агрегировать старше 30 дней
по дням/версиям, сырые строки удалять (сейчас таблица растёт без ограничения [Код] — заметка на будущее).
